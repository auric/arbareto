## Clarifications

### Session 2026-09-28

The user supplied the initial decisions directly. The follow-up answer below selects standard Git commit behavior.

- Q: Which Windows target requires initial qualification? → A: Windows 11 x64 only, not an assertion about the user's current computer. Windows 10 and ARM remain unqualified.
- Q: Which Git installation, worktree operations, and configuration changes are allowed? → A: Use installed Git for Windows. Open existing linked worktrees; do not create or manage them. Do not alter global Git configuration, identity, signing, hooks, credential helpers, PATH, or agent configuration.
- Q: What must hunk staging preserve and handle? → A: Preserve working-file bytes and unrelated index contents. Handle simultaneous staged and unstaged changes, empty or unborn repositories, and binary or unsupported diffs explicitly. Never approximate unsupported staging or unstaging.
- Q: What do local-first operation and performance figures mean? → A: No cloud account is required. Performance figures in the brief are proposed targets, not measured results.
- Q: What separates local test packages from public release? → A: Label unsigned local test packages honestly. Block public release until required signing and update checks have verified passing evidence.
- Q: Should Arbareto use standard Git commit behavior instead of promising an atomic commit of the reviewed snapshot? → A: Standard Git. Use fresh checks and unchanged approved hooks. Report late changes and any created commit accurately. Preserve the draft after an unexpected result; never retry or undo that result automatically.

### Session 2026-09-30

An answer that starts with "Reviewer default" records an analysis decision, not a user choice.

- Q: Does trust approval last longer than one application session? → A: Yes. Approval persists across launches. It binds the shared repository identity, the working copy, the selected Git installation, and the trust policy. A change to any of them requires renewed approval. Exception: the application can be unable to check every repository-controlled program file for later edits. Approval then lasts only until the application closes or its background process restarts. The confirmation states this. Revoke trust stays in the repository menu and removes the stored approval. Approval stays explicit, and missing approval never disables hooks. The stored approval holds no configuration values or credentials.
- Q: What does Changes show when a repository opens? → A: No file is selected. Changes shows the status lists with their counts, HEAD, and the hint "Select a file to view its changes".
- Q: Does this slice offer right-click menus? → A: No. Application context menus move to a later feature. The built-in page menu loses its page actions, such as Reload, Back, Save as, Print, and Inspect. Cut, Copy, Paste, and Select all stay for editable text and selected text. Every action stays reachable by a visible control and by keyboard.
- Q: Can a process that Git or a hook starts during a mutation keep running after the mutation? → A: Yes, as with command-line Git. The mutation completes when its Git process exits and its outcome is reconciled. The outcome states how many such processes still run. They block no later read. An index lock that one holds makes the next mutation refuse with the existing lock guidance. Another lock that one holds makes Git fail, as the answer below states. Closing the application ends every such process, so no application-owned process remains after closure (SC-008). Closing with only such processes and no running mutation shows no prompt. Cancellation, interruption, and a deadline still end every process of that operation. A service failure still ends the processes of each running operation. Processes from completed mutations keep running until the application closes or trust for that repository is revoked.
- Q: When is a mutation complete if a process that it started keeps writing output? → A: Reviewer default. When its Git process exits and its outcome is reconciled. The application discards output that such a process writes later. It never shows or logs that output.
- Q: What happens when a process from a completed mutation holds a lock other than the index lock? → A: Reviewer default. Git fails, and the outcome names each lock file that reconciliation observes. The outcome also states how many such processes still run and that closing the application ends them. Revoke trust ends every such process of that repository and states how many ended.
- Q: What happens when the user cancels while the application reconciles a mutation? → A: Reviewer default. Reconciliation finishes and reports the observed result. Then every process of that operation ends. Every Git step of an operation has a finite time limit.
- Q: Can the application download objects that a partial clone lacks? → A: Reviewer default. No. A download can start a program from repository configuration without approval. So no operation downloads missing objects, and approved hooks cannot download them during an operation. A read that needs a missing object shows a limited result with its reason and a remedy outside the application. A mutation that needs one fails before it changes data, or reports its reconciled result.
- Q: How long does a session-only trust approval last? → A: Reviewer default. Until the application closes or its background process restarts. After either event, the repository needs approval again. The confirmation names both events.
- Q: What does a failed commit show when a hook rejects it? → A: Reviewer default. The last part of the output from Git and the hook, bounded, as plain text. The application removes terminal control sequences, hides credentials in URLs, and never logs this output. The copyable command runs only the pre-commit hook in a terminal and never starts a commit. Other hooks show their output only in the application.
- Q: Can a whole file be staged or unstaged, including binary and renamed files? → A: Yes. Stage file and Unstage file act on one file, as Git's own whole-file staging does. They cover binary files and both paths of a staged rename. They use the same freshness checks as hunk staging and refuse a file that changed after selection. Symbolic links, submodules, filtered files, and files above the size limit get a refusal reason. Submodules get no command, and the others keep the copyable command.
- Q: Does this slice open repositories that live inside WSL? → A: Yes, repositories in WSL2 distros, opened through the `\\wsl$\` or `\\wsl.localhost\` folder paths. Out of scope: WSL1, `/mnt/c` repositories through Linux Git (they stay Windows repositories), mapped drive letters, and a watcher inside Linux. Also out of scope: external diff and merge tools, and credential or credential-manager setup. Clone, submodules across distros, and a terminal in the distro are also out of scope.
- Q: Which Git runs a WSL repository? → A: The Git inside that distro, version 2.55 or later. An older Git gets a clear refusal that names the found and the required version.
- Q: What happens when the distro of a WSL repository is stopped? → A: The application starts it on demand. It shows the status "Starting WSL distro" with Cancel.
- Q: How does a WSL repository show external changes? → A: It polls status 1 second after the previous poll ends, only while the window has focus. It also refreshes on focus and after each operation. The 2-second external-change budget on the moderate fixture stays.
- Q: Can the application own the processes that Git or a hook starts inside WSL? → A: Reviewer default. Yes, when the distro runs its systemd user session. The application then ends them at cancellation, a deadline, a background process failure, Revoke trust, and closing. A distro without that session is refused with a reason and a remedy. The 2026-10-01 answer below governs children that keep running after Git exits.
- Q: Can a WSL distro without a systemd user session run with a stated limit on process ownership? → A: No. The application refuses the distro with a reason and a remedy. The remedy tells the user to set `systemd=true` under `[boot]` in `/etc/wsl.conf`. It also tells the user to restart the distro. The application changes no distro configuration.
- Q: Does this slice initialize and update submodules? → A: Yes. One action, Update submodules, initializes and updates every submodule recursively. Each submodule goes to the commit that its parent records, as Git's own recursive update does. It is the first network operation of the slice. Single-submodule selection, adding, removing, syncing, remote-branch updates, and forced checkout stay out of scope.
- Q: How does Update submodules protect data and trust? → A: Reviewer default, with the stricter reading. A review lists each submodule, its URL without credentials, and its planned action before the start. The application refuses the update when a submodule holds a commit that no branch, tag, or other reference holds. It also refuses configured merge, rebase, or command update modes, and an interrupted clone. Programs from submodule settings and hooks need an explicit confirmation for each run. Registering submodules keeps an existing trust approval. The review and the update run fixed Git reads inside initialized submodules. None of them runs a repository program. All other reads still never start Git inside a submodule.
- Q: How do network access, credentials, and prompts work during Update submodules? → A: Reviewer default. Git's own transport policy applies unchanged. Git never waits for a prompt in a hidden terminal. A configured credential helper can show its own window. An SSH passphrase or unknown-host prompt fails. The failure shows the end of Git's output and a terminal command. Cancel, a 5-minute inactivity limit, and a 4-hour limit end a stalled update.
- Q: What speed target applies to the large-history fixture? → A: Arbareto must not be slower than Git Extensions there. Four workflows on that fixture each need a median time ratio of at most 1.0. They are cold launch, warm reopen, history refresh, and external-change display. The moderate fixture keeps its targets and its 2-second external-change budget.
- Q: Which button has focus when the commit review opens? → A: Commit staged changes. It is the default button, so Enter commits and Escape cancels. The shortcut that opens the review never commits by itself.
- Q: Does a commit message draft survive a window reload, a restart, or an interrupted close? → A: Yes. The application stores the draft of each worktree in its own storage, WSL worktrees included. The stored draft is bounded, never logged, and written atomically. It returns after a window reload, an application restart, and Interrupt and close. A successful commit or Clear message deletes it.

- Q: Which bytes does Space stage when the file's comparison is not shown? → A: Reviewer default. The current file bytes, as Git's own whole-file staging does. A change after the display refuses the action.

Git Extensions also selects the next file and shows its diff.

The empty-folder refusal protects that checkout, because Git would overwrite files there. The update checks that folder again right before it connects or checks it out.

### Session 2026-10-05

- Q: When Git refuses to open a folder (exit 128), what should Arbareto show? → A: Merged refusal. Every nonzero exit of the first discovery call gives `REPOSITORY_UNAVAILABLE`. The refusal names the selected folder and the remedy "Run `git status` in this folder". It offers no command. Its output tail shows Git's error output, cleaned by the contract §9 rules. - Q: What does the status view show when a partial clone lacks an object? → A: No entries. The status read ends with `OBJECT_MISSING` and its remedy only. A history page keeps its bounded rows (contract §7 "Missing objects").
- Q: Why can a repository ask for trust again after the first status read? → A: A protected program can change it. With the Git for Windows system configuration, `git-lfs filter-process` writes local configuration and installs hooks during the first status read. The next read ends `TRUST_CHANGED`, and the user approves again (contract §7 "Protected programs that change trust").

### User Story 1 - Install and use a Windows workspace (Priority: P1)

A developer installs Arbareto and uses familiar Windows controls without installing development runtimes or creating a cloud account.

**Why this priority**: An installed application must work outside the development environment before its desktop behavior can be qualified.

**Independent Test**: Install the packaged build as a standard Windows user. Exercise its window, folder dialog, clipboard, keyboard, and text input.

**Acceptance Scenarios**:

1. **Given** a clean qualification machine with documented prerequisites. **When** I install and start Arbareto. **Then** it runs without global Node or Bun installations.
2. **Given** a missing or unsupported Git installation or WebView2 runtime. **When** installation or startup checks run. **Then** I receive accurate prerequisites and recovery instructions, not a blank or falsely usable workspace.
3. **Given** an open workspace. **When** I accept or cancel the folder dialog. **Then** focus returns predictably, and cancellation leaves the current repository unchanged.
4. **Given** the packaged application. **When** I resize, snap, or move it between supported display scales. **Then** essential controls remain reachable and readable.
5. **Given** a commit message field. **When** I paste Unicode text or use an IME. **Then** the application preserves the text and does not commit while composition remains active.
6. **Given** keyboard-only use. **When** I navigate the primary workflow and change display density. **Then** focus remains visible, controls remain reachable, and status never depends on color alone.
7. **Given** a supported window. **When** I change themes or resize panes with a pointer or keyboard. **Then** controls remain readable, reachable, and visibly focused.

### User Story 2 - Inspect a repository before changing it (Priority: P1)

A developer opens an existing repository or linked worktree, reviews its changes, and reads recent history before preparing a commit.

**Why this priority**: Correct repository identity and accurate changes are prerequisites for safe decisions.

**Independent Test**: Open disposable fixtures with known commits and file states. Compare the displayed status, history, and selected diff with Git.

**Acceptance Scenarios**:

1. **Given** an ordinary repository with staged, unstaged, and untracked changes. **When** I open it and select the Working directory row. **Then** I see each category, including a file with both staged and unstaged changes.
2. **Given** linked worktrees with different staged contents. **When** I open either worktree. **Then** its path, branch, and staged changes identify that worktree correctly.
3. **Given** a supported text file. **When** I select its staged or unstaged entry. **Then** the diff shows the corresponding comparison and identifies its scope.
4. **Given** more than 100 reachable commits. **When** I open history. **Then** I see only the first 100 entries and a clear first-page limit.
5. **Given** a repository without commits. **When** I inspect it. **Then** history shows an empty state, while status and supported text diffs remain usable.
6. **Given** an unsupported or oversized comparison. **When** I select it. **Then** I see its status and limitation, not a misleading empty diff or enabled hunk action.
7. **Given** an invalid, inaccessible, or removed repository path. **When** I open or refresh it. **Then** I receive an actionable failure without changes to repository data.
8. **Given** a selected comparison, a draft message, and a scrolled commit panel. **When** I select a commit and then the Working directory row again. **Then** the valid selection, comparison scope, draft, scroll, and usable focus return.
9. **Given** repository state changes while commit details show. **When** I select the Working directory row again. **Then** my draft remains, but obsolete hunk selections and mutation approvals do not return.
10. **Given** linear history, merges, and commits with misleading dates. **When** I open History. **Then** graph edges match Git parents, and children appear before parents.
11. **Given** parents outside the first page or unavailable in shallow history. **When** I inspect their children. **Then** the graph identifies those boundaries rather than inventing roots or connections.
12. **Given** a selected graph row. **When** I use keyboard navigation, resize, or change density and theme. **Then** rows and graph nodes stay aligned, and equivalent parent information remains accessible without color.
13. **Given** repositories that I opened before. **When** I open the repository switcher or the start page. **Then** I see each one with its folder name and path, and Enter opens the active one.
14. **Given** a recent entry whose folder is gone. **When** I open it. **Then** I see a refusal that names the folder, and I can remove the entry. No file changes.
15. **Given** local branches, remote-tracking branches, lightweight tags, and annotated tags. **When** I open the repository. **Then** the sidebar lists each of them, and each history row shows the chips of the references that point to its commit. Nothing lets me change a reference.

### User Story 3 - Prepare exactly one selected hunk or file (Priority: P1)

A developer stages or unstages one displayed text hunk or one whole file. Working-file bytes and unrelated staged changes stay unchanged.

**Why this priority**: Incorrect partial staging can commit unintended content and destroy confidence in the application.

**Independent Test**: Use real disposable repositories with multiple hunks, binary files, renames, and existing staged content. Assert exact index contents and unchanged working-file bytes.

**Acceptance Scenarios**:

1. **Given** two unstaged hunks and existing staged changes in the same file, plus unrelated staged content. **When** I stage one hunk. **Then** only that hunk enters the index, and working-file bytes remain unchanged.
2. **Given** two staged hunks and additional unstaged edits in the same file. **When** I unstage one hunk. **Then** only that hunk leaves the index, and working-file bytes remain unchanged.
3. **Given** a displayed hunk whose file, index, or base revision changes externally. **When** I request staging or unstaging. **Then** the application refuses the stale selection and requires a new selection after refresh.
4. **Given** supported added, deleted, or untracked text, including an unborn repository. **When** I stage or unstage a hunk. **Then** the resulting index matches the selected change, including entry creation or removal where required.
5. **Given** Unicode paths, spaces, or CRLF text. **When** I stage or unstage a supported hunk. **Then** the intended path changes in the index, and working-file bytes remain unchanged.
6. **Given** a lock, conflict, binary or unsupported comparison, or overlapping application mutation. **When** I request a hunk action. **Then** the application refuses it without changing index contents or working-file bytes and explains the restriction. It never substitutes whole-file staging or an approximate hunk.
7. **Given** an empty repository with no file changes. **When** I open its change views. **Then** they show empty states, hunk actions remain unavailable, and repository data stays unchanged.
8. **Given** an index-change hook or unsupported index/monitor profile. **When** I request a hunk action. **Then** the app refuses it without bypassing integrations or publishing an index change.
9. **Given** a controlled independent write after final validation. **When** hunk publication and reconciliation finish. **Then** the external bytes remain intact, and observed late changes appear explicitly. The app does not undo publication automatically.
10. **Given** a modified binary file, an untracked file, a deleted file, and a staged rename. **When** I choose Stage file or Unstage file for each. **Then** exactly that file's index entries change, as Git's own whole-file staging changes them. Both paths of the rename return together, and working-file bytes remain unchanged.
11. **Given** a file that changed after selection, a submodule, a symbolic link, or a custom-filtered file. **When** I choose Stage file or Unstage file. **Then** the application refuses it with a reason and changes no index contents or working-file bytes.

### User Story 4 - Commit the prepared content (Priority: P1)

A developer checks the complete staged list, writes a message, and creates one local commit with the existing Git settings.

**Why this priority**: The qualification slice must complete a useful local workflow without bypassing repository safeguards.

**Independent Test**: Prepare disposable repositories with known index contents. Verify the resulting commit, branch, index, working files, and message after each outcome.

**Acceptance Scenarios**:

1. **Given** staged content, a valid message, and no concurrent or hook changes. **When** I commit once. **Then** one commit contains the approved staged content, and unrelated unstaged changes remain untouched.
2. **Given** staged content in an unborn repository. **When** I commit. **Then** the first commit succeeds and the workspace refreshes its branch, status, and history.
3. **Given** no staged changes or a blank message. **When** I attempt to commit. **Then** the application explains the missing requirement and creates no commit.
4. **Given** a staged snapshot or current branch that changed after the panel showed it. **When** I commit. **Then** the application refuses the stale request and shows the refreshed scope.
5. **Given** missing identity, denied trust, a rejected hook, or a signing failure. **When** I commit. **Then** I see the failure and retain my message without silent configuration changes or safeguard bypasses.
6. **Given** a commit interrupted after Git might have changed state. **When** reconciliation completes. **Then** I see the actual result, including any identified commit, before another mutation becomes available.
7. **Given** an approved hook stages another file after review. **When** Git creates a commit. **Then** I see its actual identity and a changed-result warning. My draft remains; the app neither retries nor rewrites the commit.
8. **Given** a controlled index or checkout change after handoff. **When** Git finishes. **Then** I see the observed result or explicit uncertainty, not a claim that preflight prevented the change.
9. **Given** a commit hook that waits for input that I cannot see. **When** I commit. **Then** after 15 seconds of silence, I see a notice with Cancel and a terminal command. The command creates no commit. The commit time limit still ends the wait, and I see the actual result.

### User Story 5 - Stay in control while Git is busy (Priority: P1)

A developer continues using the interface, sees external changes, cancels work, and closes the application without hidden activity.

**Why this priority**: Slow operations and external tools must not cause stale writes, frozen controls, or unintended background processes.

**Independent Test**: Use deliberately slow operations and concurrent external edits in disposable fixtures. Observe input response, state recovery, cancellation, and process cleanup.

**Acceptance Scenarios**:

1. **Given** a slow history or diff read. **When** I type, navigate, resize, or request cancellation. **Then** the interface acknowledges input promptly and identifies the active operation.
2. **Given** an externally changed file, index, or branch reference. **When** the application detects the change or regains focus. **Then** it refreshes affected views and invalidates obsolete hunk selections.
3. **Given** older and newer requests for different selections. **When** the older request finishes last. **Then** its result cannot replace the current selection or repository state.
4. **Given** a running operation. **When** I cancel it or it fails. **Then** I see its outcome and refreshed Git state, without a false rollback claim or automatic retry.
5. **Given** an active mutation. **When** I request application closure. **Then** I can stay or explicitly interrupt and close, with a warning that interruption cannot guarantee rollback.
6. **Given** closure during idle, read, or mutation activity. **When** the application exits. **Then** no unintended application-owned processes remain, and unrelated Git processes remain untouched.
7. **Given** an unavailable repository during recovery. **When** the application cannot determine the result. **Then** it marks state unknown. A status-only refresh keeps mutations blocked until required recovery reconciliation succeeds.

### User Story 6 - Work in a repository inside WSL (Priority: P1)

A developer opens a repository in a WSL2 distro. The developer inspects, stages, and commits with the distro's own Git.

**Why this priority**: The user added WSL2 repositories to this slice. Git for Windows cannot serve them reliably, so they need their own safe path.

**Independent Test**: In a WSL2 distro with Git 2.55 or later, open disposable repositories through both folder prefixes. Repeat the inspection, staging, commit, and lifecycle checks. Compare the results with the distro's Git, and list the distro's processes after each lifecycle event.

**Acceptance Scenarios**:

1. **Given** a repository in a running WSL2 distro. **When** I open it through `\\wsl$\` or `\\wsl.localhost\`. **Then** both paths open the same workspace, labeled "WSL: <distro>", and status, history, and diffs match the distro's Git.
2. **Given** a stopped distro. **When** I open its repository. **Then** I see "Starting WSL distro <name>…" with Cancel. Cancel leaves the current workspace unchanged, and success opens the repository.
3. **Given** a distro whose Git is older than 2.55, or whose `git` command is Git for Windows. **When** I open its repository. **Then** I see a refusal that names the found and the required version, or the Windows Git. No Git work starts.
4. **Given** a missing distro, a WSL1 distro, a computer without WSL, or a distro without a per-user service manager. **When** I open the path. **Then** I see a refusal with a reason and a remedy, and the current workspace stays unchanged.
5. **Given** a WSL repository. **When** I stage a hunk or a file and commit. **Then** the index, commit, and working-file bytes match the stories 3 and 4 rules for the distro's Git.
6. **Given** a focused window and a change made inside the distro. **When** the change completes. **Then** the workspace shows it within two seconds. Without focus, no poll runs, and focus return refreshes the workspace.
7. **Given** a hook that starts a detached process in the distro. **When** I cancel, revoke trust, or close the application. **Then** no process that the operation started remains in the distro.
8. **Given** a repository under the distro's Windows drive mount, or a worktree whose Git directory lies on the other side. **When** I open it. **Then** I see a refusal that names the mixed location.

### User Story 7 - Update submodules (Priority: P1)

A developer opens a repository whose submodules are missing or behind. The developer reviews and runs one update that brings every submodule to its recorded commit.

**Why this priority**: The user added submodule initialization and update to this slice. It is the first operation that uses the network, so it needs its own safe path.

**Independent Test**: Use disposable repositories with local submodule remotes, two levels deep. Compare each result with Git's own recursive update in a copy. Cancel a large clone, and block one checkout with local changes.

**Acceptance Scenarios**:

1. **Given** a repository with uninitialized submodules, or submodules away from their recorded commits. **When** I open it. **Then** the notice band shows the Update submodules action at once.
2. **Given** the notice. **When** I choose Update submodules. **Then** a review lists each submodule, its URL without credentials, and its planned action. Nothing starts before my explicit start.
3. **Given** a started update. **When** Git fetches, clones, and checks out submodules. **Then** I see "Fetching submodule <path> (<i> of <n>)…" or "Updating submodule <path> (<i> of <n>)…". I see a percentage where Git reports one. Every submodule reaches its recorded commit.
4. **Given** a submodule at a commit that no branch or tag holds, or with a configured merge or rebase mode. Or an interrupted clone, or a submodule folder that lost its Git link but still holds files. **When** I review the update. **Then** I see a refusal with a reason and a remedy, and nothing changes.
5. **Given** submodule settings or hooks that define programs. **When** I start the update. **Then** I must confirm those programs for this run. A declined confirmation starts nothing.
6. **Given** a submodule with local changes that block its checkout. **When** the update runs. **Then** that submodule keeps its changes, the others update, and the result names it.
7. **Given** a slow clone. **When** I cancel it, or Git shows no output and transfers no data for 5 minutes. **Then** the update stops. The result reports each changed submodule and each interrupted clone, without a rollback claim.
8. **Given** a submodule URL that needs a password or an SSH key passphrase. **When** the update runs. **Then** a prompt that Git starts directly fails at once. A prompt that waits where I cannot see it shows a notice after 15 seconds of silence. The notice offers Cancel and a terminal command. My credential helper can show its own window. A failure shows Git's output and a terminal command.
9. **Given** a submodule whose commit only a remote branch holds, and the remote deleted that branch. **When** the update fetches that submodule. **Then** the submodule keeps its commit and shows the save command. The other submodules update, and the result names it.
10. **Given** a WSL repository with submodules. **When** I update them. **Then** the distro's Git does the work inside the distro, and the results follow scenarios 1 to 9.

### Edge Cases

- A selected worktree uses a `.git` file or shares history with another worktree. Its index and working files remain distinct.
- Empty repositories, detached checkouts, and filenames containing Unicode, spaces, or option-like characters retain their correct identities.
- A file can have staged changes, further unstaged changes, or a staged deletion followed by an untracked replacement.
- External writers can change files, references, or the index without a notification. Every mutation still requires a fresh validity check.
- Locks, permission failures, full disks, removed repositories, and malformed results produce failures, not optimistic success or forced lock removal.
- Merge conflicts and unfinished merge, rebase, cherry-pick, or revert operations remain inspection-only in this slice.
- Binary content, invalid text encodings, renames, type changes, and oversized diffs never receive guessed or truncated hunk mutations.
- Repository text can resemble markup, commands, or credentials. Display it as untrusted text and keep credentials out of diagnostics.
- Trusted hooks can alter repository state before failing or completing. Reconciliation reports those changes rather than asserting unchanged data.
- Repeated commit activation, cancellation near completion, and shutdown during recovery must not create duplicate commits or conceal completed work.
- Git can normalize line endings when it reads a working file. Hunks use Git's normalized content, and raw working bytes stay unchanged. With `core.safecrlf=true`, `git add` can refuse a file that hunk staging accepts, as `git add -p` does.
- Entries marked intent-to-add, assume-unchanged, or skip-worktree show their Git status but offer no hunk actions. Git hides working changes behind the last two flags, and the app shows only what Git reports.
- A `.git` file can point to a missing directory. Git then refuses the folder, and the app shows that refusal with a remedy.
- Git refuses a folder for many setup reasons, such as another owner. Git then exits with 128 and gives no machine-readable reason. The app shows one refusal with the selected folder and Git's own message as plain text. The remedy tells the user to run `git status` in that folder. The app offers no command and never changes Git configuration.
- A path or a remote name in a copyable command can hold a double quote or a control character. It can also end in a backslash. Windows PowerShell 5.1 can pass such a value to Git as a different argument. The application then offers no command and shows the value as text.
- Windows paths can exceed 260 characters or differ only by letter case. An entry that the app cannot read, or whose file name differs in case, gets no hunk action.
- A path can contain bytes that are not valid UTF-8. Show escaped bytes, keep byte identity, and offer no hunk action.
- The superproject view shows a changed submodule commit, but not changes inside the submodule. To inspect those changes, open the submodule as its own repository.
- A partial clone can lack objects that a read or a commit needs. The app never downloads them. The affected view shows a limit with a remedy, and a mutation fails or reports its reconciled result.
- Whole-file staging can meet very large files, filtered files, and line-ending settings that make Git refuse a file. Files above the documented limit and filtered files keep only a copyable command. A Git refusal shows the end of Git's output and the same command, so a terminal run repeats Git's message.
- A writer can change a file and restore it while Git stages it. Some Git conversions depend on the index, so the application cannot always prove the staged content. Stage file then refuses with a reason and keeps the copyable command.
- Git's split index can be on, by configuration or by an existing split index file. Hunk and file staging then refuse with a reason. A private index write can change or delete shared index files.
- A WSL path can use either prefix and another letter case for the distro. Both open the same workspace.
- A WSL folder name can hold a character that Windows names cannot hold. Such a repository path is refused, and such an entry gets no hunk or file action.
- A stopped distro can take long to start. Cancel stops waiting, but the distro can keep starting, and the application never stops it.
- A WSL user's shell startup script can start an SSH agent that Git does not see. Credentials come only from the distro's Git configuration.
- Repository programs in a WSL repository run as the Linux user and can start Windows programs through WSL. Trust approval covers them as it covers Windows programs.
- A submodule URL can hold credentials. The review, the result, and every diagnostic show it without them.
- A submodule URL can name a transport that runs a command, or a local folder. Git's own transport policy blocks them unless the user's configuration allows them.
- A submodule path can hold characters that also work as a pattern. The update treats each path literally, so it never reaches another submodule.
- An update can stop during a clone and leave a half-created submodule. Git cannot continue it alone. The application names the folder to move out of the repository and never moves or deletes it.
- A submodule folder can lose its Git link and still hold files. Git would overwrite them when it reconnects a kept Git folder, so the update refuses.
- Another tool can set up a submodule between the review and its clone. The update then refuses that submodule, runs none of its programs, and keeps its commit.
- A relative hooks path in the user's own settings points inside each submodule. The update can write those hook files before Git runs them. The run confirmation covers them.
- A remote can delete the branch that holds a submodule commit. The update's own fetch can then remove the last reference to that commit. So the update checks the references again after each fetch. That submodule keeps its commit and refuses, and the others continue.
- Git's recursive initialization marks an explicitly inactive submodule active, unless configuration selects the active submodules. The review names that change.
- A submodule can need a fetch before its own nested submodules are known. The review states this. The update checks those nested submodules before it changes them, and the result lists them.
- A credential helper window can wait for the user. The inactivity limit leaves 5 minutes for it, and Cancel stays available. The FR-051 notice can appear while that window waits, so its text names a sign-in window.
- A hook or a configured SSH command can wait for input that nobody can see. After 15 seconds of silence, the status says so and offers Cancel and a terminal command.
- A nested submodule can need a program that the run confirmation did not name. That submodule stops with a reason, the others continue, and a new review lists the program.
- A deinitialized submodule keeps its Git folder, also for its nested submodules. The update reuses those folders and runs their programs. The review lists those programs, and the run confirmation covers them.
- A reused or initialized submodule fetches from the remotes in its own settings. Its first fetch ignores the URL in the repository settings, so the review shows those addresses.
- Processes from a completed mutation can keep running in a repository without trust approval. The outcome then names only closing the application, because no trust approval exists to revoke.
- A file can hold text that looks like conflict markers without a conflict. Only the unmerged entries of the index mark a conflict.
- A recent entry can name a folder that another tool moved or deleted. The open result states this, and the entry stays until the user removes it.
- Two paths can name one worktree, such as both WSL prefixes. The worktree key keeps one recent entry.
- A remote name and a branch name can both hold slashes. So the Remotes group shows each remote-tracking branch by its full short name and never splits it.
- An annotated tag can point to another tag, or to an object that is not a commit. Git peels the tag, and a chip shows only on a commit row.
- A repository can hold more references than the documented bound. The sidebar then states the limit and shows no partial list and no chips except HEAD and the current branch.
- References can change between the history read and the reference read. Chips then show only after both reads observed the same HEAD.

## Requirements *(mandatory)*

### Scope Boundaries

This feature defines qualification for one installable Windows 11 x64 slice, not production readiness or complete product coverage. This target does not describe the user's current computer. Windows 10, ARM, macOS, and Linux remain unqualified.

Include existing repositories and linked worktrees, status, supported file diffs, single-hunk staging, whole-file staging and unstaging, and local commits. Include one read-only history page with an ancestry graph. Include a list of recently opened repositories and a read-only references sidebar. Include an About window with the legal notices. Include Update submodules: the recursive initialization and update of every submodule to its recorded commit. Include repositories in WSL2 distros with the same operations, through the distro's own Git. This support runs on the Windows 11 x64 target and is not Linux desktop support.

For WSL, exclude WSL1 and `/mnt/c` repositories through Linux Git (they stay Windows repositories). For WSL, also exclude mapped drive letters and a watcher inside Linux. Also exclude external diff and merge tools, and credential or credential-manager setup. Also exclude clone, submodules across distros, and a terminal in the distro.

Exclude repository creation and cloning, remote authentication setup, and remote operations other than Update submodules. Exclude submodule selection, addition, removal, synchronization, and remote-branch updates. Also exclude branch management, history rewriting, advanced rebase, and conflict resolution. Exclude an integrated terminal, provider integrations, plugin systems, AI features, and full feature parity. Also exclude history search, pagination, line-level staging, staging several files in one action, worktree creation or management, and automatic updates. Also exclude reference actions, commit file lists, historical diffs, amend, and conflict actions.

Unsupported hunk operations do not prevent inspection of available metadata. A commit can include externally staged unsupported files when their paths, types, and staged scope remain visible and valid.

Safety uses explicit validation checkpoints, not a repository-wide transaction. Refuse mismatches detected before execution or hunk publication. These checks do not freeze independent writers or approved hooks. Reconcile observed relevant state afterward without automatic undo or retry.

Index-change hooks and unqualified index or monitor profiles exclude hunk and whole-file staging in this slice. Refuse those operations rather than bypass integrations. Ordinary commit hooks remain supported through the approved standard Git behavior.

Screen-reader (Narrator) support and its tests move to a later feature. This slice keeps native semantics and visible text labels.

### Functional Requirements

#### Installation and Windows use

- **FR-001**: The package MUST install and start for a standard Windows user without globally installed Node or Bun. Ordinary local Git work MUST require no account, AI, or network connection after prerequisites are available.
- **FR-002**: Qualification MUST report actual Git and WebView2 prerequisites, supported versions, and tested versions. It MUST distinguish bundled components, preinstalled requirements, downloads, network needs, and any elevation requirement. Missing prerequisites MUST produce installation guidance or a clear blocked state.
- **FR-003**: For a Windows repository, the application MUST use an installed Git for Windows executable. It MUST expose its selected path and version. FR-040 governs WSL repositories. It MUST NOT bundle Git, silently substitute another executable, or alter user Git configuration, including global settings. It MUST NOT alter identity, signing, hooks, credential helpers, PATH, or agent configuration. One exception exists: Update submodules lets Git register and activate submodules in the repository configuration. The review MUST name each such change before the start (FR-048).
- **FR-004**: The application MUST support folder selection, dialog cancellation, focus restoration, clipboard use, keyboard shortcuts, resizing, snapping, and DPI transitions. Text entry MUST preserve Unicode and IME composition without accidental action activation. For editable or selected text, the built-in page menu MUST offer only Cut, Copy, Paste, and Select all. Other targets MUST show no menu.
- **FR-005**: Primary actions MUST support keyboard access, visible focus, accessible contrast, and non-color status cues. The interface MUST offer compact and comfortable density with reachable controls at documented supported window sizes. Dark and light themes MUST preserve semantic change/status roles and readable text. The interface MUST remain usable in Windows contrast themes. Theme changes MUST NOT remove focus or rely on color alone. State changes MUST NOT remove focus from a control that becomes unavailable. An icon-only button MUST have an accessible name. Its tooltip MUST name the action and its shortcut key. A text button or a menu item MUST show its shortcut key as visible text.

#### Repository inspection

- **FR-006**: The application MUST open an existing ordinary repository or linked worktree and display its resolved path and checkout state. Shared history MUST NOT cause confusion between separate worktree indexes or working files. The application MUST open any layout for which Git reports a working tree, including submodule checkouts and separate Git directories. It MUST refuse bare repositories and Git administration folders with a reason and a remedy.
- **FR-007**: Status MUST distinguish staged, unstaged, untracked, and conflicted entries. One path MUST appear in each applicable category. Refresh MUST use actual Git state rather than assume earlier displayed data remains valid. Changes inside a submodule MUST stay outside these categories. A submodule gitlink MUST appear only when its checked-out or staged commit differs from the recorded commit. A conflicted entry MUST come only from the unmerged entries of the index. The application MUST NOT read conflict markers in file text.
- **FR-008**: History MUST show at most 100 commits reachable from the current checkout. Children MUST precede parents; prefer newer commits where ancestry permits. Each entry MUST identify the commit, subject, author, date, and parent relationships. The view MUST identify its checkout scope and first-page limit, and handle repositories without commits. History MUST show subjects and authors that are not valid UTF-8 with replacement characters and a visible encoding label. The commit details MUST also show the committer, the committer date, the message body, and the children on the loaded page. The same encoding rule MUST apply to the committer and the body. A body above the documented bound MUST end at a character boundary and state that it is cut.
- **FR-009**: File review MUST distinguish staged comparisons against the current commit from unstaged comparisons against the index. Untracked text MUST compare against an empty version. Unborn repositories MUST use an empty committed baseline.
- **FR-010**: Supported hunk review MUST cover UTF-8 text with LF or CRLF endings, including additions, modifications, deletions, and untracked files. Each compared version MUST contain at most 1 MiB, and the displayed diff MUST contain at most 20,000 lines. Line-ending policies are Git's built-in conversions from `core.autocrlf`, `core.eol`, `core.safecrlf`, and the `text`, `eol`, and `crlf` attributes. A file that Git reports with mixed line endings MUST have no hunk actions. A difference that Git normalizes away MUST have no selectable hunk.
- **FR-011**: Unsupported comparisons MUST show available path, status, type, and a specific limitation. Their hunk actions MUST remain disabled, and unsupported requests MUST be rejected without index or working-file changes. The application MUST NOT approximate unsupported hunk actions or silently substitute whole-file staging or unstaging. Whole-file staging MUST remain a separate explicit action (FR-038). Unsupported cases include binary files, invalid UTF-8, oversized content, renames, type or mode changes, symlinks, submodules, and LFS-managed files. Files requiring custom content filters or encoding conversion MUST also remain outside hunk support.
- **FR-012**: Reads MUST have finite output limits documented before implementation. Incomplete or truncated results MUST be identified. Mutations MUST NOT rely on incomplete data, and limits MUST NOT appear as empty or successful complete results.

#### Selected-hunk safety

- **FR-013**: A hunk action MUST publish exactly one verified, selected, currently displayed supported hunk. It MUST preserve unrelated staged entries and MUST NOT write working-file content. Without independent writers, every working-file byte, including line endings, MUST remain unchanged. Concurrent-write fixtures MUST preserve the independent writer's resulting bytes.
- **FR-014**: Before preparation, hunk actions MUST validate repository identity, base revision, complete index, working content, attributes, configuration, and operation state. Repeat relevant checks immediately before publication. Every detected mismatch MUST refuse publication and require refresh plus reselection. Never silently relocate or reinterpret a selected hunk. These checkpoints do not freeze independent writers afterward.
- **FR-015**: The application MUST prevent overlapping mutations that affect the same shared repository. This rule covers every running instance in the same Windows logon session. Across logon sessions, Git's index lock still guards each index. Linked worktrees of one repository count as the same shared repository. It MUST refuse detected stale state or lock conflicts without overwriting independent changes. Late changes MUST produce an explicit reconciled outcome, not an atomicity or rollback claim.
- **FR-016**: Conflicts and unfinished repository operations MUST block mutations in this slice. The application MUST explain the blocking state and allow refresh after external resolution. That explanation MUST show in the notice band as soon as the repository opens. It MUST NOT remove another process's lock or attempt an automatic repair. For an existing index lock, the application MUST show its path. It MUST explain that another Git process or a crash left it. It MUST tell the user to remove the lock only after all Git tools stop.

#### Commit behavior

- **FR-017**: A commit MUST cover the complete staged scope that the commit panel shows, not only the selected file or hunk. The Commit button and Ctrl+Enter MUST start it without a review dialog. Require staged changes, a complete status read, and a nonblank message. Each accepted request MUST start at most one ordinary Git commit invocation.
- **FR-018**: Immediately before handing execution to Git, revalidate the reviewed index, checkout identity, operation state, configuration, and trust. Refuse detected mismatches. Show the refreshed staged scope, and require a new commit request. After handoff, Git executes its normal commit behavior. Preflight does not atomically bind the eventual tree, parent, or destination against late changes. Reconciled intended success clears only the unchanged submitted draft; preserve later edits.
- **FR-019**: Commit MUST respect configured identity, hooks, and signing requirements. Missing identity, denied trust, hook rejection, and signing failure MUST produce actionable failures without bypasses or configuration changes. A failed commit MUST show the bounded end of the Git and hook output as plain text. That output MUST NOT contain terminal control sequences or credentials in URLs, and the application MUST NOT log it. A copyable command for a hook failure MUST NOT start a commit. When the configured commit encoding setting is not UTF-8, the application MUST refuse the commit and explain the setting. Git records that encoding and does not re-code the UTF-8 message. A commit without output and without data transfer for 15 seconds MUST show the FR-051 notice. That notice's command MUST NOT create a commit.
- **FR-020**: After every commit outcome, inspect relevant Git state and identify created commits where evidence permits. A differing result MUST appear as completed-with-effects or failed-with-effects, not ordinary intended success. Preserve the draft after failed, changed, or uncertain results. Report uncertainty rather than inventing commit attribution. Never automatically retry, reset, amend, undo, or promise rollback.

#### Responsiveness, recovery, and trust

- **FR-021**: The interface MUST remain interactive during Git activity and show pending, completed, failed, cancellation-requested, and canceled outcomes accurately. Operations MUST offer cancellation, bound diagnostic output, and distinguish incomplete work from confirmed success.
- **FR-022**: The application MUST detect external working-file, index, and reference changes and refresh affected views. It MUST invalidate stale selections, refresh on regained focus, and provide manual refresh. Obsolete results MUST NOT overwrite a newer selection or state.
- **FR-023**: After interruption or failure, the application MUST re-read relevant Git state before enabling another mutation. It MUST report completed effects, partial effects, or unknown state without assuming cancellation reversed changes. Failed reconciliation MUST block further mutations until successful recovery reconciliation. A status-only refresh MUST NOT remove that block. After a failure of the application's background process or its window, the application MUST NOT restart either automatically. It MUST say which part stopped and offer an explicit restart action. After the background process restarts, mutations MUST stay blocked until an explicit refresh. When an operation was running at the failure, that refresh MUST state that its outcome is unknown.
- **FR-024**: Closing during a mutation MUST offer staying open or explicitly interrupting and closing. The warning MUST explain rollback limits. Shutdown MUST stop application-owned activity without terminating unrelated processes or leaving unintended descendants.
- **FR-025**: Repository content and configuration MUST remain untrusted. Displayed content MUST NOT execute commands or active markup. Repository-controlled hooks, filters, previews, and tools MUST require explicit trust approval before execution. Missing trust MUST block unsafe operations rather than bypass required hooks. Reads MUST wait for trust approval when repository configuration defines a command that a read can run. A command from any configuration scope is repository-controlled when its program or hook file lies inside the repository. Commands that the application starts MUST NOT download missing repository objects. Such a download can start a program from repository configuration without approval. This rule covers every operation and the hooks that it runs. A read that needs a missing object MUST show a limited result with its reason and an outside remedy. A mutation that needs one MUST fail before it changes repository data, or report its reconciled result. Trust approval MUST persist across launches until the user revokes it. Exception: the application can be unable to check every repository-controlled program file for later edits. Approval then MUST last only until the application closes or its background process restarts, and the confirmation MUST state this. A change of repository identity, working copy, selected Git installation, or trust policy MUST require renewed approval.
- **FR-026**: The application MUST reject requests outside the supported operation set, invalid targets, and malformed inputs before changing repository data. Paths MUST retain their literal meaning, including Unicode, spaces, and option-like names. Credentials MUST NOT appear in logs or diagnostics.
- **FR-027**: This slice MUST NOT offer discard, reset, force operations, history rewrites, or automatic conflict repair. Failures and retries MUST preserve user changes and avoid unrequested repository mutations.

#### Whole-file staging

- **FR-038**: The application MUST offer Stage file for an unstaged or untracked entry and Unstage file for a staged entry. Each action MUST change exactly the index entries of that one file, as Git's own whole-file staging does. Unstaging a staged rename MUST restore both of its paths. Binary files, mixed line endings, deletions, and mode changes MUST be supported. Stage file MUST take the staged content from the working file through Git's configured built-in conversions. Both actions MUST NOT write working-file content. Each action MUST validate repository identity, base revision, complete index, attributes, configuration, and operation state before preparation. It MUST repeat these checks immediately before publication. Stage file MUST also validate that the working bytes still match the bytes of its comparison. For a shown comparison, these are the bytes that it showed. Without a shown comparison, they are the bytes that the action reads when it starts. Git's own whole-file staging also reads current bytes. Before publication, it MUST prove that the staged content matches those bytes, and it MUST refuse without that proof. Unstage file reads no working file, so its check covers the staged entry instead. Every detected mismatch MUST refuse the action and require refresh plus reselection. Both actions MUST refuse conflicted entries, submodules, symbolic links, type changes, flagged entries, and paths that it cannot read literally. Stage file MUST also refuse files that need a custom content filter and files above the documented size limit. Each refusal MUST name its reason. Space on a focused file entry MUST start the same action for that entry, with the same checks. After success from Space or the button, focus and selection MUST move to the next entry of that list. Without a next entry, they MUST move to the previous entry, then to the category heading. The newly selected entry MUST show its comparison. On a refused entry, Space MUST change nothing and MUST show the reason. When Git fails a Stage file action, the application MUST show the bounded end of Git's output. The FR-019 output rules apply. The lock and outcome rules of FR-015 and FR-016 MUST apply, and FR-025 governs trust.

#### WSL repositories

- **FR-039**: The application MUST open a folder under `\\wsl$\<distro>\` or `\\wsl.localhost\<distro>\` as a WSL repository. The prefix MUST match without regard to letter case. The distro segment MUST name one registered distro. Both prefixes of one folder MUST give one repository identity. The application MUST run Git for such a repository inside that distro, never Git for Windows. Every other folder stays a Windows repository.
- **FR-040**: A WSL repository MUST use the distro's own Git, version 2.55 or later. The application MUST find that Git once per distro and show the distro, its path, and its version. The user MUST approve it explicitly before first use, as FR-003 requires for Git for Windows. An older or unreadable version MUST give a refusal that names the found and the required version. A `git` command that is Git for Windows MUST be refused. The application MUST NOT install, update, or configure WSL, a distro, or its Git.
- **FR-041**: When the distro of a WSL repository is stopped, the application MUST start it on demand. It MUST show "Starting WSL distro <name>…" with Cancel, and the start MUST have a finite time limit. Cancel MUST leave the current workspace unchanged. The application MUST NOT stop, shut down, or unregister a distro.
- **FR-042**: A WSL repository MUST poll its status 1 second after the previous poll ends. It MUST poll only while the window has focus. It MUST also refresh on focus return, on manual refresh, and after each operation outcome. A poll MUST NOT delay a user action.
- **FR-043**: A missing distro MUST give a refusal with a reason and a remedy. So MUST a WSL1 distro, a computer without WSL, and a distro without a per-user service manager. So MUST a distro that fails to start. So MUST a distro that lacks a program that the application needs to run Git without a terminal. The same holds for a program that identifies folders, or a program that reads hook and program files. WSL repositories need `/usr/bin/perl` in the distro for that reading. A distro without it MUST give `WSL_UNAVAILABLE` with reason `no-perl` and a remedy to install perl. So MUST a folder or a distro Git without a file-system identifier, because the repository identity needs it. The identifier MUST come from the file system's own UUID. Any other identifier can change after a restart and counts as missing. The refusal MUST leave the current workspace unchanged.
- **FR-044**: The worktree and Git directories of a repository MUST all lie inside one distro, or all on Windows. The application MUST refuse any other repository. A folder under the distro's Windows drive mount counts as mixed. A WSL path that holds a character that Windows names cannot hold MUST be refused. An entry with such a path MUST get no hunk or file action.
- **FR-045**: Processes that Git or a hook starts inside a distro MUST stay application-owned. Cancellation, a deadline, a background process failure, Revoke trust, and application close MUST end them. They MUST end in the cases where FR-024 and SC-008 end Windows processes. Git and its hooks MUST run without a controlling terminal, so no hook waits for hidden input. A child that keeps running after Git exits MUST count as a lingering process, as on Windows.
- **FR-046**: Repository-controlled programs in a WSL repository run as the Linux user and can start Windows programs through WSL. FR-025 MUST apply to them unchanged. Windows environment values MUST NOT reach the distro's Git. The distro's own Git configuration and credentials MUST apply, and the application MUST NOT set up credentials. Copyable remedy commands MUST run the distro's Git through WSL.

#### Submodules

- **FR-047**: The application MUST offer one Update submodules action. It MUST initialize and update every submodule recursively, as Git's own recursive update does. Each submodule MUST reach the commit that its parent records. The application MUST run the fetches of Git's own update before the checkout of that submodule. The checkout MUST then run without another fetch. Nested submodules MUST get the same steps, one level at a time, after their parent checkout. Git's own configuration MUST decide which submodules are active. Git's own update registers an active submodule whose update mode is none, without a clone. The application MUST do the same. The action MUST NOT select single submodules or add, remove, or synchronize submodules. It MUST NOT follow remote branches or pass a force option. Git's own update checks out a reused submodule folder by force. The empty-folder refusal of FR-049 protects that checkout. Other operations MUST keep the submodule rules of FR-007, FR-011, and FR-038.
- **FR-048**: Before the start, a review MUST list each affected submodule. Each row MUST show its path, its URL without credentials, and its planned action. The actions are clone, reuse a kept submodule folder, and check out a local commit. The others are fetch and check out, no change, and skip. The review MUST name each change of the checked-out commit. A row that can fetch MUST also show the addresses that Git fetches from in that submodule, without credentials. The row MUST state when they differ from the URL in the repository settings. The review MUST name each configuration change of the update, such as registration and activation. It MUST list every program from submodule settings and hooks that the update can run. The update MUST start only after an explicit start of a current review. A relevant change after the review MUST refuse the start and require a new review.
- **FR-049**: The application MUST refuse the whole update and change nothing in nine cases. A submodule or a kept submodule folder is at a commit that no branch, tag, or other reference holds. The update can leave that commit. An existing submodule has a configured merge, rebase, or command update mode. An earlier clone was interrupted. A submodule folder without its Git link still holds files, which Git would overwrite. A submodule has no entry in the submodule configuration file. A submodule path cannot pass to Git literally. A submodule remote has a name that Git could read as an option. The repository settings set a custom location for submodule Git folders. The submodules exceed the documented limits. Each refusal MUST name its reason and a remedy. A remedy that runs Git's own update MUST state that it skips these checks and can overwrite files. The application MUST NOT remove a file or repair state. A fetch can remove the last reference to a checked-out submodule commit. So before each checkout, the application MUST check again that a reference holds that commit. A submodule that fails this check MUST keep its commit and get no checkout. It MUST show the save command, the other submodules MUST continue, and the result MUST name it. A writer can also add files to an empty reused folder during the run. So before Git connects or checks out such a folder, the application MUST check again that it is empty. A folder that fails this check MUST keep its files, and that submodule MUST end refused. Another tool can also set up a submodule after the review. So before each clone, the application MUST check again that the submodule is still not set up. A submodule that fails this check MUST end refused without a Git process. When no reference holds its commit, the result MUST name that commit. It MUST NOT offer a command, because nobody reviewed the programs of that submodule folder. Git can refuse to overwrite local changes in a submodule. That submodule MUST then keep its changes, and the result MUST name it.
- **FR-050**: Programs from submodule settings and hooks MUST run only after an explicit confirmation for that run. This covers every submodule Git folder that the update can use. Kept folders of deinitialized submodules count at every depth. It also covers hook and program files that the update writes into a submodule folder. A relative path from any settings scope can name them. The application cannot check those files first, and the confirmation MUST say so. The confirmation MUST name the submodules and the number of programs. A declined confirmation MUST start no update. A nested submodule that needs a program outside the confirmation MUST stop with a reason. Before each step that can start a program, the application MUST check the programs again. A program that changed after the confirmation MUST stop that submodule with a reason. The other submodules MUST continue. FR-025 MUST apply to the repository itself. Registering submodules MUST NOT invalidate a stored trust approval, because registration names no program.
- **FR-051**: Update submodules MUST use Git's own transport policy unchanged, and the application MUST NOT enable a transport. It is the only operation of this slice that uses the network. Git MUST NOT wait for a prompt in a hidden terminal. A configured credential helper MAY show its own window. The application MUST NOT set up or override credentials, SSH settings, or transport settings. An SSH passphrase or unknown-host prompt that Git starts directly MUST fail. The failure MUST show the end of Git's output under the FR-019 output rules and a copyable terminal command. A copied fetch command MUST apply the transport policy of the update to that one command. A configured SSH command can still wait for input that nobody can see. So a step without output and without data transfer for 15 seconds MUST show a notice. The notice MUST say that Git may wait for a hidden prompt or a sign-in window. It MUST offer Cancel and a copyable terminal command. The FR-052 limits MUST still end the step. The same notice applies to commit (FR-019).
- **FR-052**: The application MUST show "Fetching submodule <path> (<i> of <n>)…" while Git fetches. It MUST show "Updating submodule <path> (<i> of <n>)…" while Git clones or checks out. It MUST show a percentage where Git reports one. Cancel MUST stay available. An update step without output and without data transfer for 5 minutes MUST end. In a WSL repository, the data-transfer signal is the CPU time of the step, because the WSL kernel has no per-process I/O counters. So a WSL step without output and without CPU time for 5 minutes MUST end. So MUST a step that runs for 4 hours. After a cancellation, a time limit, or a failure, the application MUST re-read every submodule. It MUST report which submodules changed, fetched, or refused, and name every interrupted clone. A submodule whose Git link or registration the update wrote counts as changed. It MUST NOT claim rollback. The result MUST list each submodule in a status area above the status bar, not in a dialog. At the outcome, focus MUST move to the heading of that area. Focus in an editable field or in an open dialog MUST stay there. The outcome MUST then wait in the area.
- **FR-053**: A submodule can be uninitialized, or away from its recorded commit. The application MUST then show a notice with the Update submodules action. The notice MUST show in the notice band as soon as the repository opens. The notice MUST come from the repository's own data. Computing it MUST NOT start Git inside a submodule.
- **FR-054**: Update submodules MUST count as a mutation for FR-015, FR-016, FR-023, and FR-024. While it runs, another mutation of the same repository MUST be refused as busy. The processes that it starts MUST follow the process lifetime rules of the clarifications and FR-045. In a WSL repository, the update MUST run through the distro's Git. Its network access MUST happen inside the distro.

### Key Entities *(include if feature involves data)*

- **Repository workspace**: The selected repository, working directory, shared repository identity, checkout state, and selected Git executable. Its location is Windows or one WSL distro.

- **History page**: A captured checkout, bounded commit rows, actual parent identities, and explicit page or shallow-history boundaries.

## Assumptions

- Initial qualification targets Windows 11 x64 under a standard user account with Windows Defender enabled. Windows 10, ARM, macOS, and Linux require separate scope and qualification before support claims.
- The architecture selected in the constitution remains the candidate. This specification does not request another shell implementation or comparative prototype.
- WSL repositories need WSL2, a distro that runs its per-user service manager, and Git 2.55 or later inside the distro. The distro also needs its standard programs that detach a process from its terminal and that report file-system identifiers. It also needs `/usr/bin/perl`, which reads hook and program files and reports exact file errors. Debian, Ubuntu, and Kali always have it, because their `perl-base` package is Essential. Other distros get `WSL_UNAVAILABLE` with reason `no-perl` and a remedy to install perl. The user installs these; the application never does. WSL repositories lie on a file system whose identifier comes from its own UUID, such as the default ext4 disk.
- Update submodules needs network access to the submodule remotes and the user's own credential setup. The application sets up neither. Qualification uses local submodule remotes only.
- Users supply an existing repository and installed Git for Windows. The application opens existing linked worktrees but does not create or manage them. The plan defines supported Git and WebView2 versions and installation behavior before packaged testing.
- The first history page graphs commits reachable from the captured current checkout, not every branch in the repository. Historical file inspection, branch filtering, search, and additional pages remain deferred.
- Hunk support uses the explicit text limits in FR-010. Ordinary Git line-ending normalization remains valid, but working-file bytes must never change through staging or unstaging.
- Unsupported entries can remain visible and already staged content can still be committed. Conflicts and unfinished operations remain mutation blockers regardless of file type.
- The plan selects disposable moderate and large-history fixtures, exact hardware, minimum window sizes, and repeatable timing conditions before implementation. Performance comparisons use Git Extensions under matching conditions.
- Performance figures in the brief and numerical success criteria are proposed qualification targets, not measured results. Qualification records misses instead of silently relaxing targets.
- Automatic updates remain outside this feature. Unsigned packages are for local testing only and require explicit labeling. Required signing, update-authenticity, and tampered-update rejection checks remain public release gates.
- This specification step creates planning artifacts only. It does not scaffold the application, execute mutation tests, or claim any Windows behavior has passed.
